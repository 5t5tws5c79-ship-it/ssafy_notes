# Python 에러와 예외 처리 정리 (Exception Handling)

## 1. 버그(Bug)란?

**실제 동작과 예상된 동작의 불일치.**

> **왜 "버그"라고 부를까?**
> 코볼(COBOL)의 발명자 **그레이스 호퍼**가 발견한 일화에서 유래했다는 이야기가 유명하다. **마크 2(Mark II)** 컴퓨터의 회로에 나방(bug)이 들어가 합선을 일으켰고, 이를 로그에 기록한 것이 계기가 되었다. "버그"라는 표현 자체는 그 이전부터 (전신·전기 공학 등에서) 쓰여왔지만, 이 사건 이후로 프로그래밍 용어로 **널리 퍼졌다.**

### 디버깅(Debugging) 방법

- **`print()` 함수 활용** — 가장 기본적이고 직관적인 방법
- **개발 환경(IDE)이 제공하는 기능 활용** — 브레이크포인트, 디버거 등
- **Python Tutor 활용** — 코드 실행을 시각적으로 추적
- **"뇌 컴파일러"** — 코드를 눈으로 직접 추적하며 머릿속으로 실행해보는 것 (농담 반 진담 반이지만, 실제로 중요한 기초 디버깅 능력)

---

## 2. 에러(Error)란?

**프로그램 실행 중에 발생하는 예외 상황.**

프로그램을 실행할 때 예상치 못한 문제가 발생하면 오류가 생긴다. (예: **0으로 나누기**, **존재하지 않는 파일 읽기** 등)

### 에러의 두 종류

| 종류 | 설명 |
|------|------|
| **문법 오류 (SyntaxError)** | 콜론 누락, 오타 등 **문법적으로 잘못된** 코드. **코드 실행 전에** 감지됨 |
| **예외 (Exception)** | 문법은 맞지만 **프로그램 실행 중에 감지**되는 에러 |

---

## 3. 신택스 에러 (SyntaxError)

**잘못된 문법, 제대로 닫히지 않은 구문** 등.

- 문장이나 문자열을 **제대로 닫지 않았을 때** 자주 발생한다.
- **코드 실행 전에** 발생하기 때문에, IDE가 실행하기도 전에 미리 **밑줄이나 오류 표시로 안내**해준다.

```python
if True
    print('hello')      # SyntaxError: 콜론(:) 누락

print('hello'            # SyntaxError: 괄호가 안 닫힘
```

> 괄호, 따옴표, 콜론 누락은 **흔한 실수**이므로, 코드를 작성할 때 **항상 닫힘 여부를 점검**하는 습관을 들이자.

## 4. 예외 (Exception)

**프로그램이 잘못된 동작을 시도하려 할 때 자동으로 감지**되는 에러.

- 예: 리스트에 없는 값을 꺼내려 하면 예외 발생.
- 이런 상황을 방치하면 **프로그램이 실행 도중 그대로 뻗어버린다.** (비정상 종료)

```python
numbers = [1, 2, 3]
print(numbers[10])   # IndexError: list index out of range
```

### 내장 예외 (Built-in Exceptions)

파이썬에서 **이미 정의되어 있으며**, 특정 예외 상황을 처리하기 위해 사용된다.

- 각각의 예외는 **클래스로 구현**되어 있고, 실제로 발생하는 예외는 그 **클래스의 인스턴스**다.
- 모두 **파스칼 케이스(PascalCase)**로 이름이 지어져 있다. (`ZeroDivisionError`, `TypeError` 등)

| 예외 클래스 | 발생 상황 |
|-------------|-----------|
| `ZeroDivisionError` | 0으로 나누기 |
| `NameError` | 정의되지 않은 이름 참조 |
| `TypeError` | 타입 불일치, 인자 개수 누락/초과, 인자 타입 불일치 |
| `ValueError` | 타입은 맞지만 값이 부적절할 때 (예: `int('abc')`) |
| `IndexError` | 리스트 인덱스가 범위를 벗어남 (out of range) |
| `KeyError` | 딕셔너리에 없는 키에 접근 |
| `ModuleNotFoundError` | 존재하지 않는 모듈을 import |
| `ImportError` | import 과정에서의 오류 |
| `KeyboardInterrupt` | 사용자가 Ctrl+C 등으로 강제 중단 |
| `IndentationError` | 들여쓰기 오류 |

## 5. 예외 처리 (Exception Handling)

프로그램이 **비정상적으로 종료되지 않고, 적절하게 처리할 수 있도록 하는 방법.**

- `try`-`except` 구문을 사용해 특정 예외를 **잡아내고(catch)**, 원하는 동작을 수행한다.
- 오류 메시지를 보여주거나, **대체 로직을 실행**할 수 있다.

### 예외 처리 구성 요소

```python
try:
    예외가 발생할 만한 코드
except 예외이름:
    그 예외가 발생했을 때 실행할 코드
except:
    (위에서 안 잡힌) 나머지 예외들 처리
else:
    try가 예외 없이 무사히 끝났을 때 실행할 코드
finally:
    위 과정이 다 끝난 뒤 반드시 수행해야 할 코드
```

`try`-`except` 뒤에는 `[else] [finally]`가 **선택적으로** 붙을 수 있다.

### 각 파트의 역할

```python
try:
    num = int(input('숫자를 입력하세요: '))
    result = 10 / num
except ValueError:
    print('숫자가 아닙니다.')
except ZeroDivisionError:
    print('0으로 나눌 수 없습니다.')
else:
    print(f'결과: {result}')
finally:
    print('입력을 종료합니다.')
```

- **`try`**: 예외가 발생할 만한 코드를 넣는다.
- **`except 예외:`**: 그 예외가 발생했을 때 실행할 코드.
- **`else`**: `try`가 **예외 없이** 무사히 끝났을 때 실행되는 코드.
- **`finally`**: `try`가 성공하든 실패하든 **반드시 실행**된다. 파일 닫기, 연결 해제처럼 **반드시 마무리 지어야 하는 작업**에 사용한다.

### 왜 성공 시 실행할 코드를 `try` 안에 두지 않고 `else`로 빼는가?

`try` 블록은 **에러가 날 수 있는 부분만 최소한으로** 두는 것이 좋다.

- `try` 안에 필요 이상으로 많은 코드를 넣으면, **의도하지 않은 엉뚱한 곳에서 난 에러까지 `except`가 잡아버릴 위험**이 있다.
- 예를 들어 위 예시에서 `print(f'결과: {result}')`까지 `try` 안에 뒀다면, 만약 이 줄 자체에서 (상상하기 어렵지만) 다른 종류의 오류가 나더라도 같은 `except`에 걸려버릴 수 있다.
- 그래서 **"성공했을 때만 하고 싶은 일"은 `else`로 명확히 분리**해서, `try`는 정말 예외가 날 수 있는 부분만 감싸도록 하는 것이 좋은 습관이다.

## 6. 예외 처리 시 주의사항 — 예외의 상속 관계

**복수의 예외를 처리할 때**, 예외 클래스들의 **상속 관계**에 주의해야 한다.

> **부모 예외를 먼저 잡으면, 그 아래 자식 예외들은 잡을 수 없다.**

```python
try:
    x = int('abc')
except Exception:          # 모든 예외의 부모(조상) 클래스
    print('뭔가 에러남')
except ValueError:          # ❌ 절대 도달하지 못함!
    print('값 에러')
```

- 파이썬은 `try` 안에서 예외가 발생하면 `except`를 **위에서부터 순서대로** 검사하다가, **가장 먼저 매치되는 것**을 실행하고 끝낸다.
- `Exception`은 대부분의 내장 예외의 **최상위 부모 클래스**이므로, 이걸 먼저 두면 그 아래에 아무리 구체적인 예외(`ValueError` 등)를 적어도 **절대 실행되지 않는다.**

**올바른 순서 — 구체적인 예외를 먼저, 포괄적인 예외를 나중에:**

```python
try:
    x = int('abc')
except ValueError:          # 구체적인 예외 먼저
    print('값 에러')
except Exception:            # 포괄적인 예외는 마지막에
    print('뭔가 에러남')
```

## 7. EAFP vs LBYL — 예외 처리에 대한 두 가지 철학

### EAFP (Easier to Ask for Forgiveness than Permission)

> **"허락보다 용서가 더 쉽다."** — 예외를 중심으로 코드를 작성하는 방법. **"선조치 후보고"**

**LBYL (Look Before You Leap)**

> **"뛰어들기 전에 살펴봐라."** — 값 검사를 중심으로 코드를 작성하는 방법. `if`-`else`로 미리 조건을 검사.

### 비교표

| | **EAFP** | **LBYL** |
|---|---|---|
| 철학 | "일단 실행하고 예외를 처리" | "실행하기 전에 조건을 검사" |
| 동작 방식 | 코드를 실행하고 **예외가 발생하면** 예외 처리를 수행 | 코드 실행 **전에** 조건문 등을 사용하여 예외 상황을 **미리 검사**하고, 예외 상황을 **피하는** 방식 |
| 코드의 성격 | 예외가 발생할 수 있는 부분을 미리 예측해서 **대비하는 것이 아니라**, 예외가 발생한 **후에** 처리 | 코드가 좀 더 **예측 가능한 동작**을 하지만, 코드가 더 **길고 복잡**해질 수 있음 |
| 언제 유용한가 | **예외 상황을 예측하기 어려운** 경우에 유용 | **예외 상황을 미리 방지**하고 싶을 때 유용 |

### 코드로 비교

```python
# EAFP — try/except
try:
    value = my_dict['key']
except KeyError:
    value = None

# LBYL — if/else
if 'key' in my_dict:
    value = my_dict['key']
else:
    value = None
```

### 언제 무엇을 쓰나 — 실전 감각

- **문제 풀이·알고리즘**에서는 보통 **`if`-`else`(LBYL)** 정도로 정리하는 경우가 많다. (조건이 명확하고, 예외 상황 자체가 흔치 않기 때문)
- 반면 **실제 프레임워크·백엔드 서버**의 흐름에서는 **`try`-`except`(EAFP)**를 쓰는 경우가 많다. 예: 외부 API 호출, 파일 입출력, DB 연결처럼 **"실패할 수 있다는 게 당연한 전제"**인 작업들은, 매번 조건을 미리 다 검사하기보다 **일단 시도하고 실패하면 처리**하는 방식이 코드도 간결하고 실제 상황(네트워크 문제 등은 미리 예측이 불가능함)에도 더 맞다.
