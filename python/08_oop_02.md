# Python 객체지향 프로그래밍 정리 (OOP) — 2편 (상속)

## 1. 상속이 필요한 이유

**"교수님과 학생의 공통 행동과 차이를 나누어 파이썬으로 표현해봅시다."**

- 교수와 학생은 둘 다 **이름, 나이**를 가지고, 둘 다 **자기소개(talk)** 를 한다. → **공통점**
- 교수는 학과(department)를, 학생은 학점(gpa)을 추가로 가진다. → **차이점**

→ **공통 속성/행동은 부모 클래스(`Person`)로, 각자의 고유 특성은 자식 클래스로** 나누면 자연스럽다.

### 상속(Inheritance)이란?

부모(상위) 클래스의 속성과 메서드를 자식(하위) 클래스가 물려받는 것.

**유지보수 관점의 장점:**
- **코드 일관성**을 유지할 수 있다.
- 수정이 필요할 때 **영향 범위를 최소화**할 수 있다. (공통 로직이 한 곳에만 있으므로, 그곳만 고치면 모든 자식에 반영됨)

### 비유 — 게임 캐릭터

게임을 만든다고 하면 전사, 마법사 같은 직업군이 있다. 모두 **공격·수비·이동** 능력이 있다.

- **공통적인 속성**은 `Character` 클래스에서 구현
- **각 캐릭터별 고유 특징**은 하위 클래스(`Warrior`, `Mage` 등)에서 구현

### 자식 클래스 정의 문법

자식 클래스를 정의할 때는 **반드시 상속하려는 부모 클래스의 이름을 함께 선언**해야 한다.

```python
class Person:
    ...

class Professor(Person):    # 괄호 안에 부모 클래스 이름 명시
    ...
```

## 2. 상속 없이 구현할 경우의 문제

`Person` 클래스 하나만으로는 학생/교수 각자의 속성(gpa, department)을 담기 어렵다.

**"그럼 그냥 Student, Professor를 완전히 따로 두 개 만들면 되지 않나요?"**

→ 그러면 `name`, `age` 같은 **공통 속성과 `talk()` 같은 공통 메서드가 두 클래스에 중복 정의**된다. 나중에 "인사 문구를 바꾸고 싶다"는 요구가 오면 두 군데를 다 고쳐야 하고, 놓치면 버그가 생긴다.

→ **한곳에 공통 속성/메서드를 두고, 각자 나름의 확장을 하자** — 이것이 상속의 동기다.

## 3. 상속을 사용한 계층 구조 변경

```python
class Person:
    def __init__(self, name, age):
        self.name = name
        self.age = age

    def talk(self):             # 메서드 재사용
        print(f'반갑습니다. {self.name}입니다.')


class Professor(Person):
    def __init__(self, name, age, department):
        self.name = name
        self.age = age
        self.department = department


class Student(Person):
    def __init__(self, name, age, gpa):
        self.name = name
        self.age = age
        self.gpa = gpa


p1 = Professor('박교수', 49, '컴퓨터공학과')
s1 = Student('김학생', 20, 3.5)

# 부모 Person 클래스의 talk 메서드를 활용
p1.talk()    # 반갑습니다. 박교수입니다.
s1.talk()    # 반갑습니다. 김학생입니다.
```

- `Professor`, `Student` 어디에도 `talk()`를 **다시 정의하지 않았는데** 잘 작동한다. → `Person`에 정의된 `talk()`를 **그대로 물려받아 재사용**한 것.
- 클래스 다이어그램으로 보면, `Person`이 최상단에 있고 `Student`, `Professor`가 그 아래 가지처럼 뻗어나가는 **계층 구조(hierarchy)** 가 만들어진다.

> (다음 섹션에서 `__init__`의 중복되는 3줄(`self.name = name` 등)을 `super()`로 더 깔끔하게 줄이는 법을 배운다.)

## 4. 메서드 오버라이딩 (Method Overriding)

부모 클래스에 있는 메서드를 **같은 이름, 같은 파라미터 구조로 재정의**하는 것.

- 부모 클래스의 기능을 유지하면서도, **일부 동작만 맞춤형으로 바꾸고 싶을 때** 유용하다.

```python
class Person:
    def talk(self):
        print('안녕하세요.')

class Student(Person):
    def talk(self):             # 오버라이딩 — talk를 재정의
        print('안녕하세요! 학생입니다.')

s = Student()
s.talk()    # 안녕하세요! 학생입니다.   ← 부모의 talk가 아니라 자식의 talk가 호출됨
```

> **💡 궁금증 — 파이썬은 원래 "네임스페이스 덮어쓰기"로 이미 이렇게 동작하는데, 왜 굳이 "오버라이딩"이라는 별도 이름을 붙이나요?**
> 정확한 관찰이야. 파이썬 **내부 메커니즘**만 보면, 이건 앞서 배운 "인스턴스 속성이 클래스 속성보다 먼저 탐색된다"는 것과 완전히 같은 원리(속성 탐색 순서)가, `class → 부모 class` 방향으로 한 번 더 적용된 것뿐이다. 파이썬이 오버라이딩을 위해 **특별한 메커니즘을 추가로 만든 게 아니라**, 원래 있던 "속성 탐색(MRO를 따라가며 이름을 찾는 것)" 규칙이 자연스럽게 이 효과를 낸다.
>
> 그런데도 "오버라이딩"이라는 **이름**을 따로 붙이는 이유는, 이게 파이썬만의 구현 디테일이 아니라 **Java, C++ 등 모든 OOP 언어에서 공유하는 개념(용어)**이기 때문이다. Java/C++ 같은 정적 타입 언어는 이걸 위해 **컴파일러 차원의 별도 메커니즘(가상 함수 테이블, virtual dispatch)** 을 실제로 만든다 — 거기선 오버라이딩이 진짜로 "특수한 기능"이야. 파이썬은 그 개념을 "이미 있던 범용 속성 탐색 규칙"으로 **공짜로** 구현해낸 것뿐이지만, "부모의 동작을 자식이 같은 이름·구조로 의도적으로 교체한다"는 **디자인 패턴/의도**를 가리키는 용어로서 "오버라이딩"이라는 이름은 언어에 상관없이 계속 쓰인다.

> **💡 궁금증 — 파이썬은 자바/다트처럼 인터페이스(interface)와 구현 강제(implements) 구조가 없나요?**
> 자바·다트처럼 **문법 레벨(컴파일러)에서 강제**하는 `interface`/`implements` 키워드는 파이썬에 없다. 파이썬의 기본 철학은 **덕 타이핑(duck typing)** — "오리처럼 걷고 오리처럼 울면 오리로 취급한다", 즉 타입을 명시적으로 선언하지 않아도 필요한 메서드만 구현되어 있으면 그냥 쓴다.
>
> 다만 자바 인터페이스에 가장 가까운 공식적인 도구는 있다 — 표준 라이브러리의 **`abc`(Abstract Base Class) 모듈**이다.
> ```python
> from abc import ABC, abstractmethod
>
> class Shape(ABC):
>     @abstractmethod
>     def area(self):
>         pass
> ```
> 이렇게 `@abstractmethod`로 표시해두면, `area()`를 구현하지 않은 자식 클래스는 **인스턴스를 생성하려는 순간 TypeError가 발생**한다. 자바처럼 "정의할 때" 막는 게 아니라 "인스턴스를 만들 때" 막는다는 차이는 있지만, 실제로 강제력이 있다.
>
> 그냥 `def area(self): pass`만 써두는 건 **강제가 아니라 그냥 아무 일도 안 하는 빈 메서드**일 뿐이다. 자식이 오버라이딩을 안 해도 에러 없이 그냥 아무 동작도 안 하는 채로 상속되니, 이건 인터페이스 강제와는 다르다. "반드시 구현하게 강제하고 싶다"면 `pass`가 아니라 `abc`의 `@abstractmethod`를 써야 한다.

## 5. (참고) 오버로딩 (Overloading) — 파이썬 미지원

**오버로딩이란?** 같은 이름, **다른 파라미터**를 가진 여러 메서드를 정의하는 것. (Java, C++ 등에서 지원)

**파이썬은 오버로딩을 지원하지 않는다.** 같은 이름으로 메서드를 여러 번 정의하면, **마지막에 선언된 것만** 인식된다.

```python
class Calculator:
    def add(self, a, b):
        return a + b

    def add(self, a, b, c):     # 이전 add를 덮어씀
        return a + b + c

c = Calculator()
c.add(1, 2)          # ❌ TypeError! (2개짜리 add는 이제 없음, 마지막 정의만 유효)
```

> 대신 파이썬은 **`*args`, `**kwargs`, 기본 인자값**으로 "인자 개수가 유동적인" 상황을 유연하게 처리한다. 오버로딩이 필요해 보이는 상황 대부분은 이 방식으로 대체 가능하다.

## 6. 다중 상속 (Multiple Inheritance)

둘 이상의 상위 클래스로부터 여러 행동이나 특징을 상속받을 수 있다. (Python은 지원, **Java·Dart는 지원하지 않음**)

```python
class FirstChild(Dad, Mom):    # 여러 부모를 콤마로 나열
    ...
```

> **(참고, 시험 범위 아님) 왜 Java/Dart는 다중 상속을 지원하지 않을까?**
> 뒤에서 다룰 **"다이아몬드 문제"**처럼, 두 부모가 같은 이름의 메서드/속성을 가지고 있을 때 **"어느 쪽 걸 물려받아야 하는가"**가 모호해지는 문제가 생기기 쉽다. Java는 이 복잡함을 언어 차원에서 원천 차단하기 위해 **클래스 다중 상속을 금지**하고, 대신 상태(필드) 없이 메서드 시그니처만 갖는 **인터페이스는 여러 개 구현(implements) 가능**하게 해서 절충했다. (Java 8부터는 인터페이스에 `default` 메서드까지 가능해져 다이아몬드 문제가 다시 일부 등장하긴 하지만, 명시적 재정의를 강제해 해결한다.) 파이썬은 반대로 다중 상속을 허용하는 대신, 뒤에서 배울 **MRO(C3 선형화)** 라는 알고리즘으로 모호함을 해소한다.

### 다중 상속 예시 — 다이아몬드 형태

```python
class Person:
    def __init__(self, name):
        self.name = name

    def greeting(self):
        return f'안녕, {self.name}'


class Mom(Person):
    gene = 'XX'
    def swim(self):
        return '엄마가 수영'


class Dad(Person):
    gene = 'XY'
    def walk(self):
        return '아빠가 걷기'


class FirstChild(Dad, Mom):     # Dad를 먼저 나열
    def swim(self):             # 오버라이딩
        return '첫째가 수영'

    def cry(self):
        return '첫째가 응애'


baby1 = FirstChild('아가')
print(baby1.cry())    # 첫째가 응애    (FirstChild 고유 메서드)
print(baby1.swim())   # 첫째가 수영    (FirstChild가 오버라이딩함)
print(baby1.walk())   # 아빠가 걷기    (Dad로부터 상속)
print(baby1.gene)     # ??
```

**`baby1.gene`은 무엇이 나올까?** → **`'XY'`**

**이유:** `FirstChild(Dad, Mom)`처럼 **`Dad`가 `Mom`보다 먼저(왼쪽에) 나열**되었기 때문이다. `gene`은 `FirstChild` 자신에게는 없으므로, **먼저 나열된 부모부터 순서대로 탐색**한다 → `Dad`가 먼저 발견되고, `Dad.gene = 'XY'`가 채택된다.

## 7. 다이아몬드 문제 (The Diamond Problem)

> **"두 클래스 B와 C가 A에서 상속되고, 클래스 D가 B와 C 모두에서 상속될 때 발생하는 모호함"**
>
```
   A
  / \
 B   C
  \ /
   D
```

- **B와 C가 재정의한 메서드가 A에 있고, D가 이를 재정의하지 않은 경우라면:**
  - **D는 B의 메서드 중 어떤 버전을 상속하는가? 아니면 C의 메서드 버전을 상속하는가?**

→ 이게 바로 "모호함"의 정체다. 순서를 명확히 정하지 않으면 답이 안 나온다.

## 8. 파이썬의 해결책 — MRO (Method Resolution Order)

**MRO 알고리즘**을 사용해, **메서드를 탐색할 클래스의 순서를 미리 정의**해둔다.

**C3 선형화(C3 Linearization) 알고리즘**을 적용해 다음 원칙으로 순서를 결정한다:

1. **자식 클래스 우선**
2. **왼쪽 부모 우선** — 나열된 순서대로
3. **중복 방문 방지** — 공통 부모 클래스는 **모든 자식 클래스의 탐색이 끝난 뒤에 단 한 번만** 탐색

> 3번 규칙 덕분에, 다이아몬드 구조에서 최상위 공통 조상(A)이 **두 번 초기화되는 일**(전통적인 C++ 다이아몬드 문제의 골칫거리)이 파이썬에서는 발생하지 않는다.

### `mro()`, `__mro__` — 실제 순서 확인하기

```python
class A:
    def __init__(self):
        print('A Constructor')

class B(A):
    def __init__(self):
        super().__init__()
        print('B Constructor')

class C(A):
    def __init__(self):
        super().__init__()
        print('C Constructor')

class D(B, C):
    def __init__(self):
        super().__init__()
        print('D Constructor')


print(D.mro())
# [<class 'D'>, <class 'B'>, <class 'C'>, <class 'A'>, <class 'object'>]

print(D.__mro__)
# (<class 'D'>, <class 'B'>, <class 'C'>, <class 'A'>, <class 'object'>)
```

- `mro()`는 **리스트**, `__mro__`는 **튜플**로 같은 정보를 반환한다.
- 순서 해석: **자식 우선(D) → 왼쪽 부모 우선(B) → 다음 부모(C) → 공통 조상은 마지막에 한 번(A) → object**

## 9. `super()` 함수

**MRO에 따라, 현재 클래스의 다음 클래스(주로 부모)의 메서드나 속성에 접근할 수 있게 해주는 내장 함수.**

### `super()`의 특징

- 단순히 "부모 클래스를 직접 호출"하는 게 아니라, **MRO가 정한 올바른 순서에 따라 다음 클래스의 메서드를 찾아 실행**하기 위해 사용한다.
- **명시적으로 부모 클래스의 이름을 적지 않아도** 안전하게 부모(혹은 MRO상 다음 클래스)를 호출할 수 있다.

### 단일 상속에서 `super()` 사용 예시

```python
# super() 사용 전
class Person:
    def __init__(self, name, age, number, email):
        self.name = name
        self.age = age
        self.number = number
        self.email = email

class Student(Person):
    def __init__(self, name, age, number, email, student_id):
        self.name = name          # Person과 똑같은 코드 중복!
        self.age = age
        self.number = number
        self.email = email
        self.student_id = student_id
```

```python
# super() 사용 후
class Person:
    def __init__(self, name, age, number, email):
        self.name = name
        self.age = age
        self.number = number
        self.email = email

class Student(Person):
    def __init__(self, name, age, number, email, student_id):
        # super()를 통해 Person의 __init__ 메서드 호출
        super().__init__(name, age, number, email)
        self.student_id = student_id
```

> `super().__init__(...)`을 호출하면 `Person`의 생성자가 실행되어 **공통 속성을 먼저 초기화**한 후, `Student` 고유의 속성(`student_id`)을 이어서 추가한다. 중복 코드가 완전히 사라진다.

### 다중 상속에서 `super()` 사용 예시 — 자세히

```python
class ParentA:
    def __init__(self):
        # super().__init__()   ← 이 줄이 주석 처리된 것이 이 예제의 핵심!
        self.value_a = 'ParentA'

    def show_value(self):
        print(f'Value from ParentA: {self.value_a}')


class ParentB:
    def __init__(self):
        self.value_b = 'ParentB'

    def show_value(self):
        print(f'Value from ParentB: {self.value_b}')


class Child(ParentA, ParentB):
    def __init__(self):
        super().__init__()      # ParentA 클래스의 __init__ 메서드 호출
        self.value_c = 'Child'

    def show_value(self):
        super().show_value()    # ParentA 클래스의 show_value 메서드 호출
        print(f'Value from Child: {self.value_c}')


child = Child()
child.show_value()
"""
Value from ParentA: ParentA
Value from Child: Child
"""

print(child.value_c)   # Child
print(child.value_a)   # ParentA
```

**여기서 벌어진 일을 MRO 순서로 정확히 추적하면:**

1. `Child`의 MRO는 `[Child, ParentA, ParentB, object]`이다. (ParentA가 먼저 나열됐으므로)
2. `Child.__init__`이 `super().__init__()`을 호출 → MRO상 Child **다음**인 `ParentA.__init__` 실행.
3. `ParentA.__init__`은 `self.value_a = 'ParentA'`만 하고 끝난다. **`super().__init__()`을 호출하지 않는다** (주석 처리됨).
4. 그 결과, MRO상 ParentA **다음**인 `ParentB.__init__`은 **영영 호출되지 않는다.**
5. 그래서 `child.value_b`에 접근하면 **AttributeError**가 난다 — `ParentB.__init__`이 실행된 적이 없으므로 `value_b`라는 속성 자체가 생성되지 않았다.

> **핵심 교훈:** `super()`는 "내 부모를 호출한다"가 아니라 **"MRO 순서상 나의 다음 클래스를 호출한다."** 이 체인이 끝까지 이어지려면 **MRO에 포함된 모든 클래스가 각자 `super().__init__()`을 호출해줘야** 한다 — 이걸 **협력적 다중 상속(cooperative multiple inheritance)** 이라고 부른다. 이 예시는 `ParentA`가 그 "협력"을 하지 않아서(주석 처리) 체인이 중간에 끊기는 상황을 보여준 것이다.

## 10. `super()`는 "부모 호출"이 아니라 "MRO상 다음 호출"이다

파이썬 다중 상속에서 가장 헷갈리기 쉬운 지점이다. 질문과 답으로 정리한다.

> **깊은 궁금증 — 이거 좀 이상하지 않나요?**
> "Mom 클래스 하나만 놓고 보면 Mom의 부모는 Person이니까, `Mom.__init__` 안의 `super().__init__()`은 당연히 `Person.__init__`을 부르는 거겠지... 근데 만약 `Child(Dad, Mom)`처럼 다중 상속을 하고, `Child.__init__`이 `super().__init__()`을 호출하면 `Dad.__init__`이 불리고, `Dad.__init__` 안의 `super().__init__()`이 Person이 아니라 `Mom.__init__`을 부른다는 거잖아요. 그럼 Mom을 단독으로 선언할 때와 Child의 일부로 쓰일 때, 코드 한 줄(`super().__init__()`)이 가리키는 대상이 달라진다는 건데... 이거 모호하고 통제하기 어려운 거 아닌가요? 왜 이런 식으로 구현된 거죠?"

정확한 지적이고, 실제로 파이썬 다중 상속에서 가장 논쟁적인 특성이다.

**1) `super()`는 정적으로 정해진 대상이 아니다.**

`super()`가 무엇을 가리키는지는 그 메서드가 정의된 클래스가 아니라, 실제로 생성된 인스턴스의 MRO에 따라 동적으로 결정된다.

`Mom()`으로 단독 인스턴스를 만들면 Mom의 MRO는 `[Mom, Person, object]`라서 `super()`는 Person을 가리킨다. 하지만 `Child(Dad, Mom)`의 인스턴스를 만들면, MRO는 `[Child, Dad, Mom, Person, object]`이고, `Mom.__init__` 안의 `super()`는 "내가 속한 이 MRO에서 Mom 다음", 즉 Person을 가리킨다.

같은 코드 줄이지만, 지금 이 메서드가 어떤 인스턴스의 MRO 안에서 실행되고 있는가에 따라 다르게 해석된다. 이게 정확히 그 "모호함"의 정체다.

**2) 버그가 아니라 의도된 설계다 — 협력적 다중 상속.**

이렇게 만든 이유는 다이아몬드 구조에서 모든 조상을 정확히 한 번씩, 일관된 순서로 방문하기 위해서다.

만약 `super()`가 "내가 정의된 클래스 기준 부모"로 정적으로 고정되어 있었다면(즉 `Mom.__init__`의 super는 무조건 Person), 다이아몬드 구조에서 `Person.__init__`이 Dad 경로와 Mom 경로 양쪽에서 두 번 호출되는 전통적인 다이아몬드 문제(C++가 겪는 문제)가 그대로 재현된다.

파이썬은 이걸 피하려고 "부모"가 아니라 "전체 상속 그래프를 한 줄로 편 순서(MRO)에서의 다음 자리"를 가리키게 설계했다.

**3) 그래서 실제로 "주의해서 써야 하는" 기능이 맞다.**

이 방식은 다중 상속에 참여할 가능성이 있는 모든 클래스가, 자신이 정확히 어디에 놓일지 모른 채로 `super().__init__()`을 호출하는 것에 동의(협력)해야 안전하게 작동한다. 그래서:

- 모든 클래스가 예외 없이 `super().__init__()`을 호출해야 한다 — 하나라도 빠지면 위 예시처럼 체인이 끊긴다.
- 서로 다른 시그니처를 가진 클래스들이 섞이려면 보통 `**kwargs`를 받아서 그대로 다음으로 넘겨주는 관례를 따라야 한다.
- 이런 이유로 실무에서는 가족 관계도(Person-Mom-Dad-Child) 같은 상태를 가진 다중 상속은 거의 안 쓰고, 대신 믹스인(mixin) — 자기만의 상태 없이 기능 하나만 깔끔하게 얹어주는 작은 클래스들 — 을 조합하는 용도로만 다중 상속을 제한적으로 쓴다. (예: `class MyView(LoginRequiredMixin, ListView):`)

정리하면, "이거 통제하기 힘든 거 아닌가"라는 감각은 정확하다. 이건 동적 타이핑이라 생긴 부작용이 아니라, 다이아몬드 문제를 풀기 위해 의도적으로 선택한 트레이드오프다. 그래서 노련한 파이썬 개발자들은 상태를 가진 다중 상속은 되도록 피하고, 상태 없는 믹스인 조합 위주로만 다중 상속을 쓴다.
